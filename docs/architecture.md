# 모듈 경계

```text
네이티브 iOS 앱 / 호스트 CLI
             ↓
      Runtime · 이벤트 · 실행 예산
         ↓              ↓
 AArch32 의미론       Memory
         ↓
 A32 / T16 / T32 디코더
```

`Runtime`은 CPU 상태와 게스트 주소 공간을 소유한다. `step()`은 한 명령을 실행하고, `run()`은 주어진 명령 예산 안에서 이벤트까지 실행한다. SVC는 호스트 시스템 호출을 직접 수행하지 않는다. 임베더가 이벤트를 받아 필요한 플랫폼 동작을 구현한다.

CPU 상태는 R0–R14의 32비트 값, NZCV·Q·GE·ITSTATE, TLS, exclusive monitor와 ARM/Thumb 상태를 포함한 PC key를 보관한다. 게스트 포인터를 호스트 포인터로 직접 캐스팅하지 않는다. 주소 공간은 호스트 페이지 크기와 무관한 4 KiB 소프트웨어 페이지이며 읽기·쓰기·실행 권한을 확인한다. 게스트 실행 권한은 인터프리터의 fetch 허용 여부일 뿐 호스트 실행 메모리 권한이 아니다.

현재 한 Runtime은 호스트 스레드 하나가 소유한다. 일반 store는 exclusive reservation을 보수적으로 해제한다. 멀티 vCPU·공유 메모리의 정밀한 exclusive 모델은 아직 없다. 단일 store가 페이지를 넘다가 실패하면 아무 바이트도 변경하지 않으며, STM은 ARM 규약에 따라 오류 이전 word까지 저장할 수 있다.

후속 모듈의 경계:

| 모듈 | 입력과 출력 | 상태 |
| --- | --- | --- |
| ELF 로더 | ELF32 ARM 바이트·심볼 resolver → 게스트 매핑·export·재배치·생성자 목록 | EABI5·SysV hash·네 가지 REL 재배치 구현. [범위와 제약](elf.md) |
| Android 호환 계층 | SVC·Bionic import·JNI 호출 → 명시적 호스트 서비스 | 미구현 |
| Java/DEX 처리 | DEX·native method 연결 → 필요한 Java 객체와 JNI 동작 | 미구현 |
| iOS 플랫폼 | 수명주기·입력·파일·네트워크·그래픽·오디오 서비스 | 합성 CPU 데모만 연결 |
| AOT | 해독된 코드·재배치·간접 분기 정보 → 패키징 전에 서명할 ARM64 코드 | 조사 예정 |
| Android ARM64 | 동일 CPU 코어와 별도 플랫폼 서비스 → 보조 타깃 | 조사 예정 |

AOT는 코드와 데이터를 구별하고 간접 분기·예외·자기 수정 코드·주소 매핑을 보존해야 한다. 안전하게 번역할 수 없는 구간은 현재 인터프리터로 되돌리는 구조를 목표로 한다. LLVM에 원본 바이너리를 넘기는 것만으로 해결된다고 가정하지 않는다. 현재 성능 우위를 주장할 측정 자료는 없다.

다음 구현 순서는 scalar ELF 함수 호출 → 필요한 Bionic import → 정적 생성자 → JavaVM/JNI bootstrap → 파일·그래픽·입력 서비스다. 한 단계의 성공이 전체 앱 초기화 성공을 뜻하지 않는다. 앱별 의존성과 호출 결과는 로컬 분석 자료로 보관하며, 공개 회귀 검사는 합성 입력으로 수행한다.
