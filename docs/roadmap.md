# 로드맵: 동작하는 IPA까지

목표는 레거시 ARM32 Android 네이티브 코드를 네이티브 ARM64 iOS 앱 안에서 실행하고, 실행 가능한 IPA를 만드는 것이다. 앱 고유 입력, 분석과 산출물은 공개 저장소에 넣지 않으며 로컬 `original/`·`private/`에서만 다룬다. 공개 테스트는 합성 입력만 쓴다. 각 마일스톤은 검증 기준을 통과해야 끝난다. CI(macOS 26 ARM64/Intel, iOS SDK 컴파일)가 통과한다는 것과 실기기 실행은 별개의 주장이다.

## 원칙

- 누락된 서비스는 성공하는 no-op이 아니라 명시적 정지로 드러낸다. 서비스는 관찰된 호출에 맞춰 하나씩 추가한다.
- 게스트 주소를 호스트 포인터로 캐스팅하지 않고, 호스트 동적 로더와 호스트 syscall 전달을 쓰지 않는다. 런타임 JIT·실행 메모리 할당을 요구하지 않는다.
- Apple 전용 코드는 `platform/ios`, `platform/macos`에 둔다. macOS x86_64·arm64 호스트를 유지한다. 배포 목표는 macOS 12.0, iOS 15.0이다.
- 생성자 부작용은 롤백하지 않는다. 초기화를 다시 하려면 이미지를 다시 로드한다.
- 지금은 한 앱 구동에 집중하되, 앱별 부분(JNI 응답, 시작 순서, 입력 연결)은 어댑터로 구분해 나중에 런타임을 범용 엔진으로 분리할 수 있게 한다. 경계와 단계는 [엔진/어댑터 경계](engine-adapter.md)에 둔다.

## iCloud Drive 데이터 폴더 (M4b 확장)

지도·에셋을 iCloud Drive의 폴더에 두고 앱이 그 위치에서 바로 읽을 수 있게 한다. 기본 방식(앱 Documents 폴더)은 그대로 유지하고, 이 기능은 선택 사항이다.

- 사용자가 앱에서 폴더 선택기(`UIDocumentPickerViewController`의 폴더 선택)로 iCloud Drive의 데이터 폴더를 한 번 고른다. 앱은 보안 범위 북마크(security-scoped bookmark)를 저장해 다음 실행부터 선택 없이 접근한다.
- 앱 자체의 iCloud 권한(entitlement)이 필요 없다. 따라서 무료 계정 서명이나 사이드로딩 도구로 설치한 앱에서도 동작해야 한다.
- 파일은 기존과 같이 복사 없이 제자리에서 읽는다. 접근은 `startAccessingSecurityScopedResource`로 열고 닫으며, 읽기는 조정된 접근(`NSFileCoordinator`)을 거친다.
- iCloud가 저장 공간 절약을 위해 파일을 클라우드에만 남겨 둘 수 있다(축출). 이 경우 읽는 도중 다운로드를 기다리게 되므로 해당 폴더에 "다운로드 유지(Keep Downloaded)"를 켜도록 안내하는 것을 기본 권장으로 한다.
- 열기 전에 파일이 기기에 내려받아져 있는지 확인한다. 내려받지 않았으면 다운로드를 요청하고 진행 상태를 보여 준다. 길안내 같은 실행 중 읽기에서 지연이 생기지 않도록, 필요한 파일이 모두 로컬에 있을 때만 시작하는 것을 기본으로 한다. 끝내 읽지 못하면 조용히 넘기지 않고 명시적으로 오류를 낸다.
- 앱 업데이트나 재설치로 북마크가 무효가 되면(stale) 감지해서 폴더를 다시 고르게 안내한다. 이전 위치로 몰래 되돌리거나 자동 복사하지 않는다.
- 교체는 iCloud Drive 폴더에서 파일을 바꿔 넣는 것으로 한다. 검증(헤더·크기, 잘못된 파일 거부)은 M4b와 같다.
- 다운로드 주소와 취득 방법은 여기에도 넣지 않는다.
- 검증 기준: 합성 파일로 북마크 저장·복원·stale 처리와 미다운로드 파일 거부 테스트, 실기기에서 폴더 선택부터 읽기까지 수동 확인(iCloud는 CI로 확인할 수 없음).

## IPA 패키징 (M7)

- CI는 서명 없는 앱을 `xcodebuild archive`(`CODE_SIGNING_ALLOWED=NO`)로 만들고 `Payload/*.app`을 zip한 `.ipa`를 아티팩트로 올린다. 서명 자격과 프로비저닝은 CI에 두지 않는다.
- 설치용 서명은 사용자 개발팀 인증서로 로컬에서 하거나 사이드로딩 도구로 한다. 개인 서명 설정은 저장소에 넣지 않는다.
- 앱 고유 라이브러리와 에셋은 IPA 아티팩트에 포함하지 않는다. 사용자가 로컬에서 앱 샌드박스 영역에 주입하는 방식으로 한다.
- JIT entitlement는 요구하지 않는다. 검증 기준: 서명 후 실기기 설치·실행, 게스트 초기화 완주 로그.

## arm64 Android 패키지 (M8)

64비트 전용 기기용 arm64-v8a APK. AOT를 기다리지 않고 iOS와 같은 인터프리터 엔진과 아틀란 어댑터로 원본 ARM32 라이브러리를 돌린다. 그래픽은 기기의 GLES2로 그대로 넘기고(번역 없음), 오디오는 OpenSL ES, 위치는 `LocationManager`, HTTPS는 `HttpURLConnection`이다. 원본 앱에 없던 화면은 넣지 않는다. 로컬에서만 만들고 디버그 키로 서명하며 공개 저장소·아티팩트에 올리지 않는다. 구조와 빌드는 [Android](android.md).

- 진행: APK 빌드(서버), 실제 게스트의 GLES 경로를 Mesa로 헤드리스 확인. 남은 것은 실기기 실행 확인, 백그라운드 위치, 뒤로 간 동안의 프레임 정책. M6(AOT)가 생기면 같은 APK에서 번역 코드로 바꿔 비교한다.

## 랜딩 페이지 (M9)

앱이나 지도가 업데이트될 때를 대비한 안내 페이지다. 내용은 런타임이 무엇인지, 지원 상태와 알려진 제한, 사용자가 가져온 파일을 교체하는 방법, 변경 이력으로 한정한다. 원본 앱의 이름·바이너리·다운로드 주소·취득 방법은 싣지 않고, IPA도 서명 없는 런타임 셸만 안내한다. 호환 정보는 형식 버전과 검증 결과만 일반적으로 표시한다. 구동이 안정된 뒤에 만든다.

## 앱 업데이트 대응 (M10)

사용자가 새 버전이나 갱신된 원본 `.so`를 가져와도 호환성 문제가 바로 드러나게 한다.

- 누락 감지(엔진, `engine/shell/session.cpp`): 모든 호스트 서비스를 묶은 뒤 아무도 제공하지 않는 import를 `compat missing_import`(데이터 심볼은 `compat missing_data`)로 실행 전에 모두 적는다. `JNI_OnLoad` 직후에는 어댑터의 시작·프레임 진입점과 입력 바인딩이 부르는 네이티브 중 이미지에 없는 것(`compat missing_entry`, `compat missing_native`)을, `JNI_OnLoad`와 init 뒤에는 게스트가 ID를 얻었지만 호스트 구현이 없는 Java 메서드(`compat jni_unhandled`, `JavaBootstrap::unhandled_methods`)를 적는다. 조용히 넘기지 않고, 실제 호출 시점에는 지금처럼 이름을 대고 정지한다(`missing_service=`, 데이터 심볼 읽기는 `missing_data=`, Java 메서드는 `no host implementation for`). 세션은 로드한 라이브러리의 SHA-256도 `library sha256=`으로 남긴다.
- 검증된 빌드 목록: 앱에 넣어 두지 않고 이 저장소 main의 `adapters/atlan/verified_versions.json` 한 파일을 런처가 시작할 때(그리고 앱이 다시 활성화될 때 몇 분 간격으로) raw GitHub 주소로 받아 Application Support에 저장한다. 받지 못하면 마지막으로 받은 사본을 쓰고, 그것도 없으면 상태를 "확인 불가"로만 보인다. 실행은 막지 않는다. 새 빌드를 검증하면 이 파일에 한 줄을 더하는 것만으로 설치된 앱에 반영되고 IPA를 다시 깔 필요가 없다.
- 목록 형식(1): `{"format": 1, "updated": "YYYY-MM-DD", "builds": [{"name", "version", "sha256"}]}`. 빌드는 패키지 안 네이티브 라이브러리의 SHA-256으로 식별하고(같은 버전 문자열로 다시 포장하거나 고친 라이브러리를 검증된 것으로 착각하지 않게), 이름·버전은 표시용이다. 이 세 키 말고는 받지 않으므로 다운로드 주소나 메모가 공개 파일에 섞이지 않는다(`tests/package_tests.cpp`가 저장소의 파일도 검사). 항목은 `atlan-verified-entry <ATLAN 폴더>`로 만든다.
- 주소는 `adapters/atlan/verified_versions.hpp`의 `verified_list_url` 하나다. 비공개 어댑터 저장소로 옮기면 raw 주소를 인증 없이 받을 수 없으므로 GitHub Pages나 별도 서버 같은 공개 위치가 따로 필요하다.
- 런처의 설정 › 버전 정보가 현재 폴더 패키지의 라이브러리 해시를 목록과 대조해 "검증된 버전 / 검증되지 않은 버전 / 확인 불가"를 보이고, 목록의 빌드와 그 기준일을 보여 준다. 해시는 경로·크기·수정 시각별로 한 번만 계산한다.
- 랜딩 페이지(M9)를 만들면 같은 JSON에서 표를 만든다. 형식 버전과 검증 결과만 일반적으로 적고, 원본 앱의 바이너리·다운로드 주소는 넣지 않는다.
- 원본이 64비트 전용으로 바뀌면 현재의 ARM32 런타임으로는 실행할 수 없으므로 별도의 ARM64 지원이 필요하다. 이는 이 마일스톤 범위 밖이며, 필요해지면 따로 계획한다.
- 검증: 합성 이미지로 누락 import 목록(`tests/shell_tests.cpp`), 진입점·입력 네이티브 누락 목록(같은 파일의 합성 어댑터), 구현 없는 Java 메서드 목록(`tests/abi_tests.cpp`), 호출 시 정지(`import_tests`, `abi_tests`), 목록 파싱·거부·해시(`tests/package_tests.cpp`). 런처의 받기·저장·표시는 CI로 확인할 수 없어 실기기에서 본다.

## 범용 엔진 분리 (M11)

런타임(ARM32 인터프리터, ELF 로더, libc·pthread, GLES2→Metal, OpenSL ES)은 특정 앱에 거의 묶여 있지 않으므로, 구동이 안정된 뒤 다른 ARM32 네이티브 라이브러리에도 쓸 수 있는 범용 엔진으로 떼어낼 수 있다. 지금은 앱 하나에 집중하고 구조만 준비한다.

- 앱별로 달라지는 부분(JNI 응답과 Java 쪽 역할, 시작 순서, 터치·위치 연결, 데이터 파일 규약)은 어댑터로 구분한다. 엔진은 어댑터를 모른다.
- 경계, 모듈 분류, 충돌 없는 단계별 리팩터 순서는 [엔진/어댑터 경계](engine-adapter.md)에 있다. 단계 0~4는 진행 중인 작업과 겹치지 않게 병행하고, 디렉터리 이동(단계 5)은 진행 중 브랜치가 정리된 뒤 한 번에 한다.
- 현재는 한 앱이 부르는 함수만 구현하므로 다른 앱은 빠진 함수를 채워야 한다. M10의 누락 감지를 엔진 기능으로 둬서 그 목록을 바로 보이게 한다.
- 공개 범위: 엔진만 공개 대상이다. 원본 앱의 바이너리, 분석 자료, 다운로드 주소와 취득 방법은 계속 `original/`·`private/`에만 둔다. CPU 코어의 GPL-2.0-or-later 출처 때문에 분리 전에 파일별 SPDX와 출처를 다시 확인한다.
- 진행: 단계 0~3과 5 완료. 엔진은 `engine/`(`atlan_runtime`, `atlan_shell`)에, 아틀란 고유 코드는 모두 `adapters/atlan/`(`atlan_adapter`)에 있다. 세션은 `AppAdapter`(`engine/shell/app_adapter.hpp`)로만 앱을 안다. 남은 것은 공개 API 정리와 저장소 분리 판단(단계 6).
- 검증 기준: 합성 어댑터만으로 엔진 단독 테스트가 통과하고, 엔진 디렉터리 코드에 앱 고유 이름·상수가 없다.

### 추후: 공개 엔진 + 비공개 앱 저장소 (M11 단계 5·6 이후)

지금은 GitHub Actions(macOS·iOS 빌드)를 무료로 쓰려고 공개 저장소 하나에서 개발한다. 분리가 끝나면 다음 구조로 옮긴다.

- 범용 엔진은 공개 저장소에 남기고, 앱 어댑터는 비공개 저장소에서 엔진을 서브모듈이나 패키지로 가져와 빌드한다.
- 지금 사용자가 기기 Documents에 따로 넣는 앱별 파일(예: 네이티브 대체용 시그니처 파일, 입력 바인딩)은 비공개 저장소의 CI가 IPA 번들에 함께 넣는다. 앱은 번들에 든 파일을 기본값으로 쓰고, Documents에 같은 파일이 있으면 그쪽을 우선한다.
- 비공개 저장소의 macOS 러너는 분당 사용량이 10배로 계산된다. iOS 빌드만 돌리고, 엔진 테스트는 공개 저장소에서 돌린다.
- 원본 바이너리에서 얻은 데이터를 담은 IPA는 개인 사용 전용이다. 공개 릴리스·아티팩트로 올리지 않는다. 엔진이 GPL-2.0-or-later 출처라서, 다른 사람에게 배포하면 그 IPA의 소스 공개 의무도 따라온다.
- 그때까지는 지금처럼 앱별 파일을 기기에 따로 넣는다.
- 아틀란 전용 런처(Atlan iOS Launcher, 홈 화면 이름 "Atlan")는 `adapters/atlan/ios/`에 있다. 첫 실행(ATLAN 폴더 넣기·선택, 자동 시작 묻기), 시작 화면(APP·UI·MAP·Sys 폴더와 앱 패키지를 백그라운드로 점검하고 앱·지도·안전운전 버전 표시), 설정(일반·지도 데이터·버전 정보·개발자)을 담는다. 문구는 `launcher_text.h`, 색과 크기는 `launcher_style.*`에 모아 둬서 시안이 바뀌어도 그 두 파일과 화면 조립부만 고치면 된다. 버전 읽기와 폴더 점검은 `adapters/atlan/data_status.*`(C++, 테스트 있음).
- 앱 화면 오른쪽 아래의 홈 버튼(`SendMsgFromAtlan` 5번)은 어댑터가 `AtlanAdapter::Config::on_home`으로 넘기고, iOS 셸은 그때 런처를 게스트 위에 띄운다(게스트는 아래에서 계속 돈다). 노치 쪽 여백(`platform/ios/main.mm`의 `notchInsets`)은 런처 설정에서 켜고 끈다.
- 다른 위치(iCloud Drive 등)에서 고른 ATLAN 폴더는 보안 범위 북마크로 기억하고, 어댑터가 `GuestStdio::add_mount`로 그 폴더를 제자리에서 읽힌다. 앱이 쓰는 `ATLAN/NAND`는 앱 Documents에 남는다. 아직 iCloud에서 내려받지 않은 파일을 미리 걸러내는 점검은 없다.

## 위험

- 그래픽, 오디오, 입력은 가장 큰 미지수다. M4 시작 전에 관찰된 호출 목록으로 범위를 다시 정한다.
- 순수 인터프리터는 프레임 단위 연산에 느릴 수 있다. M5 프로파일 결과로 M6의 AOT 범위(전체 또는 뜨거운 함수만)를 정한다.
- iOS 기기 검증이 없는 동안 iOS 동작은 "컴파일됨"으로만 보고한다.
